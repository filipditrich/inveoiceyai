Automation surfaces — [MCP](/docs/integrations/mcp), the [Slack agent](/docs/integrations/slack) —
authenticate with a bearer token. There are **two kinds**, and the difference matters.

|            | Personal key                          | Ops key                                       |
| ---------- | ------------------------------------- | --------------------------------------------- |
| Created in | **Settings → API keys**               | A deployment environment variable             |
| Identifies | You                                   | The deployment                                |
| Workspace  | Your default workspace                | The configured default workspace              |
| Revocable  | Yes, individually, from the UI        | Only by changing the variable and redeploying |
| Use for    | Your own Cursor, Claude Code, scripts | Shared infrastructure, the Slack bot          |

Prefer a personal key. It is attributable and you can revoke it on its own.

## Creating a personal key

**Settings → API keys → give it a name → Create.**

The key is displayed **once**. Copy it immediately — it is not recoverable afterwards, and losing it
means creating a new one and revoking the old.

Name keys after where they live: `cursor-laptop`, `claude-code`, `billing-script`. When you later
need to revoke one, the name is the only thing telling you which is which.

Requests carry it as an ordinary bearer token:

```bash
curl -X POST https://your-host/api/mcp \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

## What a key grants

A personal key resolves to **your user**, and operates against **your default workspace**.

Within that workspace it is full access. There are no scopes and no read-only variant: a holder can
list invoices, create them, issue them, mark them paid, and email them to your clients.

Treat the key like a password: it can change financial records and send email to clients.

<Callout
  type="warn"
  title="A key is not limited to the workspace you are looking at"
>
  It binds to your **default** workspace, not whichever one your browser session
  currently has active. If you belong to several, check which one that is before
  assuming an automation is writing where you think it is.
</Callout>

The one real containment: `create_invoice` injects the issuer from a server-side
[preset](/docs/guides/issuers#presets-for-automation). A model cannot invent a bank account or IČO
onto your invoice, regardless of what it is asked to do.

## Revoking

**Settings → API keys → Revoke.** Immediate, and scoped to that one key — everything else keeps
working.

Revoke whenever a key has been in a shared config file, a screenshot, or a chat you no longer trust.
Key creation and revocation are both written to your security audit log under
**Settings → Security**.

## The ops key

`MCP_API_KEY` is an environment variable on the deployment. It authenticates as the deployment
itself, against the configured default workspace, with no user attached.

Use it only for shared infrastructure such as the Slack bot or CI. It is not attributable, and
rotation requires a redeploy of every client that uses it.

| Variable                | Gates                                     | When unset                      |
| ----------------------- | ----------------------------------------- | ------------------------------- |
| `MCP_API_KEY`           | `/api/mcp`, and `/eve/v1/*` as a fallback | Only personal keys are accepted |
| `EVE_API_KEY`           | `/eve/v1/*` over HTTP                     | Falls back to `MCP_API_KEY`     |
| `CRON_SECRET`           | `/api/cron/overdue-reminders`             | Reminders never fire            |
| `RESEND_WEBHOOK_SECRET` | `/api/webhooks/resend`                    | The webhook rejects all events  |

Generate one with:

```bash
openssl rand -base64 48
```

Everything fails closed. An unset key never means "open" — it means that path is refused.
