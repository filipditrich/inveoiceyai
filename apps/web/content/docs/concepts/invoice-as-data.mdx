---
title: An invoice is data
description: The single schema every surface in Invoicey validates against.
---

Most invoicing tools model an invoice as a document with fields attached. Invoicey inverts that: an
invoice is a **validated data structure**, and the PDF, the ISDOC XML and the payment QR are three
renderings of it.

This is not an aesthetic preference. It is what makes the rest of the product possible.

## One schema, every surface

There is exactly one definition of what an invoice is — a Zod schema called `InvoiceSchema`. The web
form, the [MCP tools](/docs/integrations/mcp), the [Slack agent](/docs/integrations/slack), the PDF
renderer and the ISDOC generator all parse against it.

```text
web form ─┐
MCP       ─┼─▶ InvoiceSchema.parse() ─┬─▶ PDF
Slack     ─┘         │                ├─▶ ISDOC XML
                     │                ├─▶ SPAYD QR
                     ▼                └─▶ database row
              rejected if invalid
```

The practical consequence: **no surface can create an invoice the others cannot understand.** There
is no "the API accepts fields the UI doesn't" drift, because there is no separate API model.

It is also what makes AI-driven creation trustworthy. When an assistant in Cursor proposes an
invoice, the schema is the referee. A missing DUZP, a malformed IČO, a due date before the issue
date — all rejected, with a specific error the model reads and corrects. The assistant cannot talk
its way past validation.

## The shape

```ts
const InvoiceSchema = z.object({
  meta: InvoiceMetaSchema, // doc type, number, dates, currency
  issuer: IssuerSnapshotSchema, // who is invoicing — frozen at issue
  client: ClientSnapshotSchema, // who is billed — frozen at issue
  vat: InvoiceVatSchema, // VAT mode and cross-border flags
  payment: PaymentSchema, // bank account, symbols, method
  items: z.array(InvoiceItemSchema).min(1),
  totals: TotalsSchema, // per-rate breakdown and grand total
  notes: z.string().max(2000).optional(),
  customization: InvoiceCustomizationSchema.optional(),
});
```

Field-by-field detail is in the [schema reference](/docs/reference/invoice-schema).

## Validation is strict on purpose

The schema encodes Czech invoicing law rather than being permissive and hoping for the best:

| Rule                                         | Enforced                           |
| -------------------------------------------- | ---------------------------------- |
| IČO is exactly 8 digits                      | `/^\d{8}$/`                        |
| DIČ is `CZ` + 8–10 digits                    | `/^CZ\d{8,10}$/`                   |
| PSČ is 5 digits                              | `/^\d{3} ?\d{2}$/`                 |
| Bank account is `prefix-number/bankCode`     | `/^(?:\d{1,6}-)?\d{1,10}\/\d{4}$/` |
| IBAN is Czech                                | `/^CZ\d{22}$/`                     |
| Due date is not before the issue date        | cross-field check                  |
| Credit notes reference the corrected invoice | conditional requirement            |
| At least one line item                       | `.min(1)`                          |

Defaults are applied by the caller _before_ validation, never silently at parse time. If a required
field is absent, you get an error naming it — you do not get an invoice with a guessed value.

<Callout type="warn" title="This bites when automating">
  Because nothing is silently defaulted, an assistant that omits `duzp` gets a
  validation error rather than an invoice dated today. That is the intended
  behaviour. It is also the single most common reason a first automated
  `create_invoice` call fails.
</Callout>

## Totals are computed, then verified

Line items carry quantity, unit price and VAT rate. Totals are derived from them — grouped per VAT
rate, then summed.

When you issue, the totals are recomputed server-side and compared against what was submitted. A
mismatch aborts the whole transaction. A client that miscalculates cannot persist a wrong total,
which matters when the client is a language model.

## Currency and language

Both are literals in the schema: `CZK` and `cs`. Not configuration — literals.

Multi-currency and multi-language invoices are a real amount of domain work (exchange-rate dates,
per-country VAT rates, translated legal notes) and pretending to support them with a dropdown would
produce invoices that are subtly wrong. They are out of scope until done properly.
